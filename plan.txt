================================================================================
1. PROJECT OVERVIEW
================================================================================

Furniture-first design tool. Local now, SaaS later.

The user describes a piece or a kitchen/wardrobe run (optional sketch).
The system produces:

  1. An editable floor plan (top view)
  2. One editable front elevation per wall
  3. Photoreal image(s) covering those walls, after the drawings are locked

Drawings are data rendered in a web app. Pictures are generated only after
lock, from sealed camera jobs. An image model never invents the plan or the
elevation.

Primary: furniture and kitchen/wardrobe runs. Rooms/buildings later.

================================================================================
2. THE RULE
================================================================================

Plans are data. Elevations are data. Renders are pictures.
Those jobs never share a tool.

  - Code owns all geometry. No model computes a coordinate, ever.
  - LLM talks, extracts facts, and CHOOSES OPERATIONS. It does not author
    layout arithmetic and it does not author markup.
  - The web app draws the spec. Every drawn thing is a real element with
    the id the chat uses.
  - The user edits the spec (drag / type / chat). Both paths run the same
    validated operations.
  - Code plans photoreal cameras from the wall graph.
  - The image model receives one sealed shot packet at a time.

Corollary: if a state would be invalid, it must be unrepresentable.
Prefer a schema that cannot overflow over a validator that catches overflow.

================================================================================
3. WHY BUILD 1 FAILED  (evidence, not opinion)
================================================================================

Recorded so these are never rebuilt the same way.

3.1  "Two doors next to each other" was impossible, not misunderstood.
     BaySpec was width + a flat modules list. svg_elevation drew every
     module at full bay width, and `count` repeated it VERTICALLY. Side-by-
     side fronts had no representation. The model complied as best it could.
     No prompt fix exists for a missing degree of freedom.
     -> Section 5: recursive openings.

3.2  Drawings framed badly at every size.
     svg_markup declared "1 user unit = 1 cm", then used PAD = 48 (48 cm of
     padding), stroke 1.2 (a 12 mm line) and font size 7 (7 cm lettering).
     On a 320 cm wall that reads as ~3% text height. On a 60 cm cabinet the
     padding is wider than the object and the text is 14% of it.
     Model space and paper space were the same coordinate system.
     -> Section 6: two spaces, a scale ladder, fixed paper annotation.

3.3  Nothing checked vertical fit.
     validate_spec summed bay widths against wall length, but never checked
     module heights against (height - cornice - plinth). _draw_bay stacked
     upward from the floor, so an overflowing stack drew ABOVE the carcass —
     outside the frame. Second, independent cause of 3.2's symptom.
     -> Section 5: flex sizing makes overflow unrepresentable.

3.4  Plan corners overlapped.
     geometry.place_walls started the next wall at prev.back_end and rotated
     90°. Two 60 cm-deep runs met in a 60x60 cm square occupied twice, and
     both walls counted that corner in their bay sums.
     -> Section 7: explicit corner resolution, usable length.

3.5  Hit targets were a second implementation of the layout.
     editor/drawings.py re-derived ELEV_PAD_*, inner_top, inner_h and the bay
     cursor. Any renderer edit silently desynced clicking from drawing.
     -> Section 8: one layout solver, dumb backends.

3.6  Every chat edit rewrote the whole document.
     SPEC_PATCH_PROMPT said "Return the FULL updated spec JSON". That allows
     collateral drift, produces no diff, and gives the user nothing to
     approve before it lands. This is the mechanism behind 3.1 going
     unnoticed, not just its consequence.
     -> Section 10: named edit ops, restate, ghost preview, confirm.

3.7  "Ask if unclear" was an instruction with no mechanism.
     See Section 15 references: models recognise ambiguity but keep it latent
     unless the output CONTRACT forces it out.
     -> Section 10: required ambiguities[] and a clarify/propose branch.

5. SOURCE OF TRUTH — SPEC v2
================================================================================

One JSON document. Plan and every elevation are renderings of it.
If a number is wrong on screen, the spec is wrong — not the picture.

Walls are first-class. Bays belong to a wall. A bay is an OPENING TREE.

5.1  THE OPENING TREE  (the fix for 3.1 and 3.3)

Industry practice, not invention: cabinet CAD models a carcass as openings
divided by partitions, recalculating neighbours to fit (CabinetCRUNCHER's
"Opening System"; ArchiWood's vertical divisions / front splits / reveals).

An opening is a node:

  {
    "id": "row-1",                       // unique among SIBLINGS only
    "label": "",
    "split": "rows" | "cols" | null,     // null = leaf, carries a front
    "children": [ <opening>, ... ],      // only when split is set
    "size_cm": 20,                       // fixed extent along parent's axis
    "flex": 1,                           // OR a share of what remains
    "front": {                           // leaves only
      "type": "door|drawer|open|glass|appliance|panel|false_front",
      "hinge": "left|right|top|bottom|none",
      "handle": "bar|knob|j_pull|none",
      "count": 1                         // INPUT SHORTHAND — see below
    }
  }

SIZING RULE (this is what kills the overflow bug):
  Along a split axis, fixed `size_cm` children are laid out first; every
  `flex` child divides the remainder in proportion. A tree therefore ALWAYS
  fits its parent exactly. Overflow is not a validation failure — it is
  not expressible.
  Invalid only if sum(size_cm) > parent extent. That is one check, at one
  place, with a clear message.

ONE RULE AT EVERY LEVEL:
  A wall's `bays` list IS a "cols" split whose extent is the wall's usable
  length (Section 7.2). Bays are ordinary openings — they may be fixed
  (size_cm) or flex. "Three equal bays" therefore needs no arithmetic from
  the model. There is exactly one sizing rule in the system.

SIZE IS AXIS-NEUTRAL:
  Every opening uses `size_cm`, never `width` or `height`. A child of a
  rows split is sized vertically; the same field name means "extent along
  my parent's split axis" everywhere. The UI may still say "width" to the
  user when the axis is cols.

ADDRESSING:
  Ids are unique among siblings. The global address is the PATH —
  "wall-a/bay-2/row-1/col-0" — resolved segment by segment, like a
  filesystem. Paths are the vocabulary shared by the drawing, the chat and
  the ops (Section 9.1).

COUNT IS INPUT SHORTHAND, NORMALISED AWAY:
  A model may write {"type":"drawer","count":3}. Validation expands that
  into a rows split of three flex drawer leaves. A stored spec never has
  count > 1. Two representations of one thing would force a special case
  into the solver and every op; normalising keeps the input natural and the
  stored form canonical. It also makes each drawer addressable, so "make
  the top drawer taller" resolves to a real node.

REVEALS:
  wall.reveal_mm (default 3) is the gap between adjacent fronts. Fronts are
  inset by half a reveal on each shared edge. This is what makes an elevation
  read as cabinetry instead of a wireframe.

"Two doors next to each other on the top part" is now one operation:

  { "id":"bay-2", "width":90, "split":"rows", "children":[
      { "size_cm":60, "split":"cols", "children":[
          { "flex":1, "front":{"type":"door","hinge":"left"}  },
          { "flex":1, "front":{"type":"door","hinge":"right"} } ] },
      { "flex":1, "front":{"type":"drawer","count":3} } ] }

5.2  DOCUMENT

{
  "project_id": "uuid",
  "version": 1,
  "units": "cm",
  "name": "human-readable name",

  "layout": {
    "type": "straight | L | U | galley | custom",
    "walls": [
      { "id":"wall-a", "label":"Wall A — sink run", "length":320,
        "adjacent_to":["wall-b"], "faces":[], "sequence":0,
        "corner": { "start":null, "end":"yield" } }
    ]
  },

  "walls": [
    { "id":"wall-a",
      "height":220, "depth":60, "reveal_mm":3,
      "cornice": { "type":"straight", "height":8 },
      "plinth":  { "type":"recessed", "height":12 },
      "side_columns": { "left_cm":8, "right_cm":8, "detail":"plain" },
      "bays": [ { "id":"bay-1", "label":"Sink", "size_cm":80,
                  "split":"rows", "children":[ ... ] } ] }
  ],

  "materials": { "carcass":"", "doors":"", "finish":"" },
  "hardware":  { "style":"", "placement":"" },
  "brief":     "locked facts from intake, verbatim where possible",
  "assumptions": [ "plinth 12 cm — professional default, not client-stated" ],
  "render_notes": "photoreal request (lighting, mood) — never geometry"
}

5.3  INVARIANTS  (server-enforced, every write)

  I1  layout.walls ids == walls ids.
  I2  adjacent_to and faces are symmetric; no pair is both.
  I3  FIT. In any sibling group (bays of a wall, children of a split):
        sum(fixed size_cm) <= parent extent, and
        if no sibling is flex, sum(fixed) == parent extent +/- 1.0 cm.
      The parent extent for a wall's bays is its usable length (7.2).
      This is the ONLY sizing rule. It applies identically at every depth.
  I4  Ids are unique among siblings. Every path resolves to one node.
  I5  A leaf has a front; a split node has >= 2 children and no front.
  I6  A stored front never has count > 1 (normalised — see 5.1).
  I7  Walls listed in each other's faces[] never share a camera.
  I8  Every assumption the system made is in assumptions[], in cm.

  FIT_TOLERANCE_CM = 1.0 at every level. All fixed sizes are human- or
  model-authored and carry the same kind of slop; computed sizes use flex
  and are exact by construction, so they need no tolerance.

Island / peninsula is not a wall unless it has its own designed face.

================================================================================
6. TWO SPACES — THE SCALE SYSTEM  (the fix for 3.2)
================================================================================

The single most important rule in the renderer.

  MODEL SPACE  = the real object, in cm. Never drawn directly.
  PAPER SPACE  = the sheet, in mm. Everything drawn is in mm.
  scale        = model -> paper, chosen from a fixed ladder.

6.1  SHEET
  Sheet is A3 landscape proportion, 420 x 297 mm, margin 10 mm,
  title block 40 mm tall along the bottom.
  On screen: 1 mm = var(--px-per-mm), default 96/25.4. On print: real mm.

6.2  SCALE LADDER  (ISO 5455 preferred reduction scales)
  1:1, 1:2, 1:5, 1:10, 1:20, 1:50, 1:100
  Pick the LARGEST scale at which content + margins + dimension bands fit
  the drawing area. Never scale-to-fit continuously — snap to the ladder,
  then centre. A 40 cm nightstand and a 6 m run then produce sheets that
  look like the same drawing set.
  Print the chosen scale in the title block: "SCALE 1:20".

6.3  ANNOTATION IS CONSTANT, IN MM  (ISO 3098 heights)
  dimension text      2.5 mm
  labels / bay names  3.5 mm
  sheet title         5.0 mm
  Text NEVER scales with the object. That is the whole point.

6.4  LINE WIDTHS  (ISO 128-20 ladder; thick:thin >= 2:1)
  0.70 mm  carcass outline, wall footprint outline
  0.35 mm  partitions, cornice/plinth bands, bay dividers
  0.25 mm  front outlines, shelf lines
  0.18 mm  dimension lines, witness lines, hatching, centrelines
  In SVG use vector-effect="non-scaling-stroke" so zoom never thickens a
  line. In CSS these are literal `border-width` values in mm.

6.5  DIMENSIONS
  Two bands under each elevation: overall width, then per-bay widths.
  One band at the left: overall height. Cornice and plinth get their own
  witness dimensions when non-zero. Numbers come from the spec, never from
  measuring the drawing.

================================================================================
7. GEOMETRY — THE LAYOUT SOLVER
================================================================================

One module. Pure functions. No I/O, no framework, no model.
It is the only place coordinates are produced.

  solve_elevation(spec, wall_id, sheet) -> Sheet
  solve_plan(spec, sheet)               -> Sheet

  Sheet = {
    scale: 20,
    sheet_mm: {w, h},
    boxes:  [ { id, kind, x_mm, y_mm, w_mm, h_mm, stroke_mm, front, label } ],
    lines:  [ { id, kind, x1,y1,x2,y2, stroke_mm } ],
    texts:  [ { id, x_mm, y_mm, mm, anchor, value } ],
    hits:   [ { id, path, x_mm, y_mm, w_mm, h_mm } ]   // addressable nodes
  }

`hits` is emitted BY the solver, from the same numbers as `boxes`. There is
no second layout pass anywhere in the system (kills 3.5).

`path` is the stable address of a node — "wall-a/bay-2/row-1/col-0" — and is
the vocabulary shared by the drawing, the chat, and the edit ops.

7.1  ELEVATION SOLVE
  carcass rect -> subtract cornice band, plinth band, side columns
  -> lay out bays left to right by width
  -> recurse the opening tree: fixed children first, flex divides remainder
  -> inset each front by reveal/2 on shared edges
  -> emit dimension bands
  Recursion is depth-first, deterministic, and total.

7.2  PLAN SOLVE — CORNERS  (the fix for 3.4)
  Walls are placed along the sequence chain, turning 90 deg at each corner.
  At every corner exactly one wall YIELDS: its run is shortened by the
  neighbour's depth, and the neighbour occupies the corner square.

    usable_length(wall) = length
                          - depth(neighbour) for each end where corner=="yield"

  I3 validates bay widths against usable_length, not raw length. The corner
  square is drawn once, tagged as the yielding wall's corner unit, and
  labelled (blind corner / corner unit / return).
  Default: the LATER wall in sequence yields. The user can flip it.

7.3  TESTS
  Golden files for: straight, L, U, galley, four-wall.
  Property tests, all randomly generated specs:
    - every child box lies inside its parent box (no overflow, ever)
    - sibling boxes never overlap beyond the reveal
    - sum of child extents == parent extent, within 0.01 mm
    - every `hits` entry matches a `boxes` entry exactly
    - chosen scale is on the ladder and content is inside the margins
  If a test needs a prompt to pass, the solver is wrong.

================================================================================
8. RENDERERS — ONE SOLVER, DUMB BACKENDS
================================================================================

Renderers contain no arithmetic. They translate a Sheet into markup.

  A. ElevationDOM (React, HTML+CSS)   — the editing surface
     Nested divs, sizes in mm, borders from the 6.4 ladder. Every node is a
     real element carrying data-path, so hit-testing, hover, selection,
     focus, keyboard nav and ghost previews are free browser behaviour.

  B. PlanSVG (React, SVG)             — the plan
     Rotated wall footprints, corner squares, bay ticks, dimension lines.
     vector-effect="non-scaling-stroke".

  C. SheetSVG (shared, TS)            — export
     The SAME Sheet -> flat <rect>/<line>/<text>. Used for photoreal
     reference images and for PDF/print.

Because A and C consume one Sheet, the reference image handed to the image
model cannot disagree with what the user approved.

At lock: the browser renders SheetSVG for the plan and every elevation,
rasterises to PNG, and POSTs both to the server with the frozen spec.

================================================================================
9. THE EDITOR
================================================================================

Direct manipulation and chat are the same operations on the same spec.

9.1  ON-DRAWING VOCABULARY
  Every bay and every opening shows its short label (BAY 2, ROW 1, COL 0)
  at 3.5 mm. The user can therefore SAY what they can SEE, and the model
  answers in the same tokens. Most "it changed the wrong thing" failures are
  reference failures; shared vocabulary removes them at the source.

9.2  DIRECT
  - click a node -> inspector shows its path, size, front, material
  - type a size -> set_size
  - drag a divider -> set_size on the two siblings (live, snapped to 1 cm)
  - split / merge buttons on the selected node
  - undo/redo over the op log

9.3  CHAT
  Same ops, chosen by the model. Never a document rewrite. See Section 10.

9.4  OP CATALOGUE  (server-side, validated, the only mutators)
  set_size(path, cm) | set_flex(path, n)
  split(path, axis, count | ratios) | merge(path)
  set_front(path, type, hinge?, handle?, count?)
  insert_bay(wall, index, width) | delete_bay(path)
  set_wall(wall, height? depth? length? cornice? plinth? reveal?)
  set_corner(wall, end, yield|take)
  set_materials(...) | set_hardware(...)
  Every op: validate -> apply -> re-run invariants -> bump version ->
  append to the op log. A rejected op returns why, and changes nothing.

9.5  LOCK
  Freeze the version, rasterise sheets, move to render.

10. AGENTS
================================================================================

Two language jobs. No council. No chairman.

  INTAKE   google/gemini-3.7-flash, reasoning_effort high, vision
           Conversation, sketch reading, question asking.
  STRUCTURE openai/gpt-5.6-terra, reasoning {effort: "max"}
           Brief -> spec. Utterance -> ops. The hard reasoning.
           Verified available: 1.05M context, text+image+file,
           supports reasoning_effort AND structured_outputs.

Both calls use response_format json_schema with strict: true, and
provider.require_parameters: true so requests only route to endpoints that
honour it. Delete the fenced-JSON scraping path once this is live.

10.1  INTAKE AGENT
  Keeps build 1's good instincts: cm only, do the math, no praise, a photo
  is a crop so out-of-frame is unknown rather than absent, max 3 questions
  per turn, options for visual choices, closed topics stay closed.

  Adds a structured contract — the mechanism that replaces the council:

    {
      "notice":      [ {q, a}, ... ],       // private self-ask
      "locked":      [ "wall-a length 320 cm", ... ],
      "open":        [ {field, why_it_matters, options[]} ],
      "assumptions": [ {field, value_cm, rationale} ],
      "confidence":  0.0-1.0,
      "response":    "client-facing text",
      "status":      "chat" | "ready"
    }

  `open` and `assumptions` are REQUIRED and may not both be empty while
  status is "chat". A model that has nothing open and nothing assumed is
  claiming certainty and must justify it.

  COMPLETENESS GATE (code, not judgement):
  A typology profile lists the fields a maker needs (envelope, top, bottom,
  sides, per-bay stack, appliance clearances, hardware, materials,
  junctions). status cannot become "ready" while a required field is
  neither locked nor explicitly assumed. The model cannot talk its way past
  the gate; it can only close fields or record a default.

10.2  STRUCTURE AGENT — BRIEF -> SPEC
  Input: locked brief + assumptions. Output: spec v2 against the JSON Schema.
  On invariant failure, return the failure text and retry once. Twice failed
  = surface it, do not loop.
  The model authors STRUCTURE (how many bays, what splits, which fronts).
  Code authors GEOMETRY. Widths use flex wherever the brief did not state a
  number, so a valid spec is the default outcome.

10.3  STRUCTURE AGENT — EDIT  (the fix for 3.1's silence and 3.6)
  Input: the utterance, the current spec, the visible paths of the wall on
  screen, and the current selection.
  Output:

    {
      "understanding": "restate the change in drawing vocabulary",
      "targets":       [ "wall-a/bay-2/row-0" ],
      "ops":           [ ... ],
      "ambiguities":   [ {question, options[]} ],
      "confidence":    0.0-1.0,
      "action":        "clarify" | "propose"
    }

  Routing:
    action=="clarify", or confidence < 0.75, or ambiguities non-empty
      -> ask, in chat, WITH OPTIONS. Change nothing.
    otherwise
      -> apply to a scratch copy, render it, show a GHOST PREVIEW:
         removed nodes hatched red, added nodes hatched green, changed
         dimensions called out. "Apply" / "Cancel" / "Not what I meant".
    "Not what I meant" feeds the rejected ops back as a negative example
    for the next attempt on the same utterance.

  Nothing mutates the real spec until the user confirms. The user always
  sees the change as a DRAWING before it exists.

10.4  WHY THE CONTRACT, NOT THE INSTRUCTION
  See Section 15. Models detect ambiguity but keep it latent unless the
  output format forces disclosure; structured uncertainty raises coverage
  while REDUCING question count. "Be cautious" is not a mechanism. A
  required field is.

11. VIEW PLANNER + PHOTOREAL  (kept from build 1, it was correct)
================================================================================

Code, not a model. Inputs: layout.walls. Outputs: elevation jobs, camera jobs.

ELEVATION JOBS
  One per wall.id. Count is len(walls). Never asked of a model.

CAMERA JOBS
  Constraint: at most two walls per shot.
  Constraint: walls in each other's faces[] never share a shot.
  Constraint: every wall appears in at least one shot.
  Constraint: no two shots have the same wall set.

  Adjacent chain: pair along the chain, ceil(n/2) shots. For U, overlap the
    shared back wall (A+B, then B+C) — two inside-corner photos.
  Facing / galley: two frontal shots. Never one.
  Four-wall cycle: two OPPOSITE inside corners, e.g. (A,B) and (C,D).

  Worked cases (unit tested):
    straight 1 wall  -> 1 elevation, 1 frontal
    L, 2 adjacent    -> 2 elevations, 1 corner shot
    U, 3 chain       -> 3 elevations, 2 shots (A+B, B+C)
    galley, 2 facing -> 2 elevations, 2 frontal shots
    four walls       -> 4 elevations, 2 opposite-corner shots

SEALED PACKET  (one OpenRouter image call each)
  camera type (frontal | inside_corner)
  LEFT / RIGHT wall ids and their bay lists
  only those walls' elevation PNGs (from Section 8C)
  the plan PNG with that camera cone marked
  locked materials/finish + render_notes
  an explicit exclude list of every other wall id

The image model never sees all elevations at once and never chooses how many
images exist. A bad shot regenerates from the same packet.

PHASE 3 — RENDERERS                                            COMPLETE
  ElevationDOM (HTML/CSS, mm, ISO line ladder), PlanSVG, SheetSVG.
  gpt-5.6-terra at effort "max" authors these three components against the

================================================================================
14. KEY DESIGN DECISIONS
================================================================================

1.  Code owns geometry. Models own language and structure choices.
2.  Invalid states are unrepresentable where possible (flex sizing) rather
    than merely validated.
3.  Two spaces: model cm, paper mm, snapped to an ISO scale ladder.
    Annotation size is constant and never scales with the object.
4.  One layout solver. Renderers are dumb. Hit targets come from the solver.
5.  Elevations are HTML/CSS because a cabinet elevation IS a nested box
    layout, CSS supports real mm units, and every node becomes an
    addressable element for free. The plan is SVG because CSS cannot rotate
    wall runs.
6.  Edits are named, validated operations — never document rewrites.
7.  No change reaches the spec without the user seeing it drawn first.
8.  Ambiguity is a required output field, not a hoped-for behaviour.
9.  Completeness is a code gate over a typology profile, not model diligence.
10. The drawing and the chat share one vocabulary: node paths, shown on the
    drawing.
11. Two models, two jobs: gemini-3.7-flash talks, gpt-5.6-terra structures.
    Adding a third opinion is the old council. Do not.
12. Photoreal cameras come from adjacency code. Max 2 walls per shot.
    Facing walls never paired. References sealed per shot.
13. terra at max effort writes the renderer once, offline. It does not draw
    designs at runtime.
14. Island is not a wall unless it has a designed elevation face.
15. All model traffic goes through OpenRouter.

Drafting standards — Section 6
  ISO 128-20 / ISO 128-2 line width ladder 0.13-2.0 mm, thick:thin >= 2:1
    https://cdn.standards.iteh.ai/samples/1408/f62555427b87436eafe1e6abc5271860/ISO-128-20-1996.pdf
  National CAD Standard plotting guidelines (fine/thin/medium/wide)
    https://www.nationalcadstandard.org/ncs5/pdfs/ncs5_pg.pdf
  ISO 3098 lettering heights 1.8 / 2.5 / 3.5 / 5 / 7 / 10 mm
  ISO 5455 preferred scales and "SCALE 1:n" designation
    https://www.iso.org/standard/11500.html

Cabinet data modelling — Section 5
  CabinetCRUNCHER "Opening System": add vertical/horizontal partitions,
  auto-recalculate surrounding parts to fit the carcass
    https://cabinetcruncher.com/cabinet-cutlist-software
  ArchiWood: parametric cabinets, movable vertical divisions, drawer stacks,
  front splits, numeric reveals
    https://archiwood.github.io/

Why code owns geometry — Section 2
  LLM layout/spatial performance degrades 42%->80%+ as geometric complexity
  rises; FloorplanQA isolates exactly this failure on structured coordinate
  layouts
    https://arxiv.org/html/2507.07644v3
    https://arxiv.org/html/2509.16891

Why ambiguity must be a required field — Sections 10.1, 10.3
  "Knowing but Not Showing": models recognise ambiguity but the awareness
  "remains largely latent ... they do not reveal that uncertainty unless
  they are asked to"
    https://arxiv.org/html/2605.25284v1
  SAGE-Agent: structured-uncertainty-guided clarification gives 7-39% higher
  coverage while asking 1.5-2.7x FEWER questions
    https://arxiv.org/html/2511.08798

Model + API facts — Sections 4, 10
  openai/gpt-5.6-terra-20260709: 1.05M ctx, text+image+file, supports
  reasoning, reasoning_effort, structured_outputs, tools.
  google/gemini-3.7-flash-20260813: 1.05M ctx, multimodal, structured_outputs.
  OpenRouter reasoning effort accepts "max" (~95% budget) for GPT-5 series;
  "max gives GPT-5.6 even more time than xhigh to reason and explore
  alternatives, run checks, and revise its approach".
  Structured outputs: use json_schema + strict:true and
  provider.require_parameters:true so only honouring endpoints are routed.
    https://openrouter.ai/docs/guides/features/structured-outputs
    https://openrouter.ai/docs/use-cases/reasoning-tokens

SVG technique — Section 8
  viewBox + preserveAspectRatio for fit; vector-effect="non-scaling-stroke"
  so line weight stays true under zoom
    https://developer.mozilla.org/en-US/docs/Web/SVG/Attribute/preserveAspectRatio
