================================================================================
1. PROJECT OVERVIEW
================================================================================

Furniture-first local design tool.

The user describes a piece or a kitchen/wardrobe run (optional sketch).
The system produces:

  1. An editable floor plan (top view)
  2. One front elevation per wall (N walls → N elevations)
  3. Photoreal image(s) covering those walls, after the drawings are locked

Drawings are data rendered in a web app. Pictures are generated only after
lock, from sealed camera jobs. An image model never invents the plan or
the elevation.

Target: local app, single user.
Primary: furniture and kitchen/wardrobe runs. Rooms/buildings later.

================================================================================
2. THE RULE
================================================================================

Plans are data. Elevations are data. Renders are pictures.
Those jobs never share a tool.

  - LLM talks, extracts facts, writes/patches a Furniture Spec (JSON).
  - Web app draws the spec as SVG (plan + one elevation sheet per wall).
  - User edits the spec (drag / type sizes / chat). Canvas updates instantly.
  - Code plans photoreal cameras from the wall graph.
  - Image model receives one sealed shot packet at a time. It does not
    choose how many images, or which walls.

No council. No chairman writing floor-plan prompts. No image-model
technical drawings.

3. TECH STACK
================================================================================

Reuse from the old codebase: OpenRouter client, image encode/save,

Do not reuse: council, chairman, DSD-as-image-prompt, generation
wrappers for floor plan / elevation.

4. MODELS (via OpenRouter)
================================================================================

v1 uses one LLM for every language job (brief, spec JSON, chat edits):

  LLM:     google/gemini-3.7-flash
           (multimodal. User switched from qwen/qwen3.8-max on 2026-08-15.)
           Fallbacks if quality is weak: qwen/qwen3.8-max, x-ai/grok-4.6,
           or anthropic/claude-opus-4.6 — swap the id, do not add a council.

  Image:   photoreal only. Current: google/gemini-3.1-flash-image-preview
           (replace later if a better renderer exists; never used for
           plan or elevation).

Three named models in parallel is the old council. Do not do that.

================================================================================
5. SOURCE OF TRUTH — FURNITURE SPEC
================================================================================

One JSON document. Plan view and every elevation are renderings of it.
If a number is wrong on screen, the spec is wrong — not the picture.

Walls are first-class. Bays belong to a wall. Modules belong to a bay.

{

  "project_id": "uuid",
  "version": 1,
  "units": "cm",
  "name": "human-readable name",

  "layout": {
    "type": "straight | L | U | galley | custom",
    "walls": [
      {
        "id": "wall-a",
        "label": "Wall A — Sink run",
        "length": 320,
        "adjacent_to": ["wall-b"],
        "faces": [],
        "sequence": 0
      }
    ]
  },

  "walls": [
    {
      "id": "wall-a",
      "height": 220,
      "depth": 60,
      "cornice": { "type": "straight", "height": 8 },
      "plinth":  { "type": "recessed", "height": 12 },
      "side_columns": { "left_cm": 8, "right_cm": 8, "detail": "plain" },
      "bays": [
        {
          "id": "bay-1",
          "label": "Bay 1 — far left as you face this wall",
          "width": 80,
          "modules": [
            { "type": "drawer", "height": 20, "count": 3, "handle": "bar" },
            { "type": "door",   "height": 180, "handle": "bar" }
          ]
        }
      ]
    }
  ],

  "materials": { "carcass": "", "doors": "", "finish": "" },
  "hardware":  { "style": "", "placement": "" },
  "brief":     "locked facts from the consultant, verbatim where possible",
  "render_notes": "user's photoreal request (lighting, mood) — not geometry"
}

Island / peninsula is NOT a wall unless it has its own designed face.
It may appear in a photoreal shot as an object in the room, recorded
under render_notes / a separate objects list — not as a fake fourth wall.

Rules:
  - Bay widths on a wall must sum to wall.length (within 1 cm, or the
    spec is invalid and must not render).
  - adjacent_to is symmetric. faces is for parallel opposite runs.
  - A wall in faces[] of another wall must never share a camera.

================================================================================
6. PIPELINE — THREE STAGES
================================================================================

------------------------------------------------------------------------------
STAGE 1 — BRIEF (one LLM, chat)
------------------------------------------------------------------------------

Same job as the old consultant. No reviewer behind it.

- Mode from context: sketch/photo analysis, or design-from-scratch.
- Exhaustive intake via notice (self-ask), not a skip-list.
  Each turn the model must answer: what this piece is; what a maker
  of this type needs; what the client already locked; what is still
  open. Client questions come from those gaps (max 3, with options).
  Cornice/plinth/hardware are examples of forgotten maker details,
  not the whole list. The list is generated from the typology.
- Maximum 3 questions per turn. Options for visual details.
- Sketch upload is in. A photo is often a zoomed crop; out of frame
  is unknown, not absent. Several detail shots are fragments of one
  object. Vision may only lock what is actually visible. More photos
  can be attached on later turns.
- Output when confirmed: locked brief text + a first Furniture Spec
  JSON (the model writes the spec; code validates it).

The brief is facts. It is not an image prompt.

------------------------------------------------------------------------------
STAGE 2 — PLAN + ELEVATIONS (web editor)
------------------------------------------------------------------------------

The spec is drawn, not imagined.

Plan view (one SVG):
  Top-down footprints of every wall run, thicknesses, bay ticks,
  corner meeting, dimension labels when numbers exist.

Front elevations (N SVGs):
  One sheet per wall.id. Nested rectangles: carcass, bays, modules,
  cornice band, plinth band, handles as marks, dimension labels.
  Looks like CAD (black line, white fill). Not photoreal.

v1 editor (tweak, not full CAD):
  - AI builds the first spec from the brief.
  - User selects a bay/wall, types a size, drags a divider.
  - Or chats: "Bay 2 is 90 cm, open shelves." LLM returns a JSON patch.
  - Both views update from the same spec. No image generation here.

Lock:
  User confirms the drawings. Spec version is frozen for render.
  SVG exports are saved (plan + each elevation).

------------------------------------------------------------------------------
STAGE 3 — RENDER (image model, after lock)
------------------------------------------------------------------------------

Code builds camera jobs from the wall graph (Section 7).
Each job is one OpenRouter image call with a sealed packet:

  - Camera type (frontal | inside_corner)
  - LEFT of frame / RIGHT of frame wall IDs and bay lists
  - Only those walls' elevation SVGs as reference images
  - Floor plan SVG with that camera cone marked
  - Locked brief materials/finish + user's render_notes
  - Explicit exclude list of other wall IDs

The image model never sees every elevation at once.
Two jobs must not have the same wall set.

User reviews the photos. A bad shot is regenerated from the same
packet, not "try a new prompt and hope."

================================================================================
7. VIEW PLANNER (CODE, NOT A MODEL)
================================================================================

Inputs: layout.walls (ids, adjacent_to, faces, sequence).
Outputs: elevation jobs + camera jobs.

ELEVATION JOBS
  For each wall.id: one front-elevation SVG.
  Count is len(walls). Never asked of a model.

CAMERA JOBS  (photoreal)

  Constraint: a shot shows at most two walls.
  Constraint: walls that face each other cannot share a shot.
  Constraint: every wall.id appears in at least one shot.
  Constraint: no two shots have the same set of wall ids.

  Adjacent chain (straight / L / U / sequential custom):
    Pair along the chain. Number of shots = ceil(n/2).
    Odd leftover: last shot is frontal on the remaining wall,
    OR overlap the shared corner (U-shape: A+B then B+C).
    Overlap is preferred for U: two inside-corner photos.
    Duplicate of the same pair is a bug. Overlap of the shared
    back wall is correct.

  Facing / galley (two walls in faces[], not adjacent):
    Two frontal shots. Never one shot. ceil(n/2) is wrong here.

  Four-wall cycle:
    Two opposite inside corners, e.g. (A,B) and (C,D).
    Not two adjacent corners that leave a wall uncovered.

Each camera job is a record:

  {
    "shot_id": "shot-1",
    "camera": "inside_corner" | "frontal",
    "walls": ["wall-a", "wall-b"],
    "frame": { "left": "wall-a", "right": "wall-b" },
    "exclude": ["wall-c"],
    "references": ["elev-wall-a.svg", "elev-wall-b.svg", "plan-cone.svg"]
  }

Worked examples:

  Straight, 1 wall:  1 elevation, 1 frontal photo.
  L, 2 adjacent:     2 elevations, 1 corner photo (A left, B right).
  U, 3 chain:        3 elevations, 2 photos (A+B, B+C).
  Galley, 2 facing:  2 elevations, 2 frontal photos.
  Four walls:        4 elevations, 2 opposite-corner photos.

The planner is unit-tested with these cases. If a test needs a
prompt to pass, the planner is wrong.

================================================================================
11. KEY DESIGN DECISIONS
================================================================================

1. Furniture-first. Rooms/buildings are not v1.

2. One spec, two kinds of drawing: 1 plan + N elevations.

3. N walls → N elevation sheets. Count comes from wall IDs.

4. Photoreal cameras come from adjacency code, not from the
   image model. Max 2 walls per photo. Facing walls never paired.
   Isolated references so two shots cannot be the same walls.

5. Working drawings are SVG. Photoreal is the only raster generate.

6. One LLM in v1. Image model is a different job, not a second
   "council member."

7. v1 editor is tweak + chat, not a full CAD wall-drawing tool.

8. Sketch upload stays.

9. Island is not a wall unless it has a designed elevation face.

10. All LLM/image calls still go through OpenRouter.

11. Quality over speed, but no multi-model debate tax.
